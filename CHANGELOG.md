## [Unreleased]

### Added

- Open an interactive session when the client starts with no arguments — `forgel-code` now shows a prompt and stays open instead of printing usage text. A sentence typed at the prompt is handed to the engine's project agent as one free-form request and the agent's answer is shown in the session. The session shows the selected project and lets the owner switch it without leaving, shows a plan as its ordered tasks with their states and a new task with its title and state, and re-reads the task and release state from the engine on its own so progress appears without asking for a status. Accepting a task, sending it back with remarks, retrying a failed task, pausing and resuming work are asked for in plain language, an ambiguous or unmatched request gets a clarification and performs nothing, a failure shows the reason and the next possible step while the session stays usable, and replies follow the language of the owner's message. Adopting a repository, creating a project, secrets and configuration stay explicit separate actions that a sentence never triggers, key material never reaches the screen, and leaving — or the end of the input — ends the session at once. The session adds no capability: every answer and every piece of state still comes from the engine, and every one-shot usage keeps its previous output, exit status and `--json` form.

### Changed

- Speed up the suite without weakening a test — the expensive duplicated work is gone instead of a scenario: one read-only checkout copy and one prepared installation per scenario group are shared by the tests that only read them, and the bounded-check cases configure a limit below the product default.
- Remove every statement of a suite completion time, duration or runtime bound from the documentation — the README `## Tests` section still says that one documented command runs the whole suite, that the installer situations are covered by a real installation into a throwaway home location with a real detected login shell, and that a run from a source checkout needs only the Python standard library and no network access, but it no longer promises how long such a run takes.

### Fixed

- Mask the value of the French password label when it is written with underscores or hyphens — the label is now recognised as a secret label in its joined spellings as well as its spaced one, in any letter case, so an engine reply or error that carries it next to a value is redacted before display and before retention. Every value form already handled for the spaced label is covered, a joined label without an adjacent value leaves the message unchanged, and every other supported label in every language redacts exactly as before.
- Refuse sensitive explicit actions phrased in French and Spanish as well as in English and Russian — a free-text request to create a project, to set or define a credential such as a password, a token or a key, or to change configuration or settings is recognised in all four languages the session speaks, in either word order, in ordinary inflections and with or without diacritics. The refusal-and-redirect answer speaks the language of the message, states that such an action is never carried out from a sentence, and then points at the client's own explicit command `forgel-code` together with the action it performs — creating a project, setting or defining a password, a token or a key, or changing the configuration — in the same style as the English and Russian refusals. Nothing of the refused request is sent onward, ordinary French and Spanish conversation still reaches the engine unchanged, and English and Russian results stay exactly as they were.
- Mask the credential of a label followed by an ordinary descriptor word — a secret label followed by a word such as `value`, `field` or `string` used to hide that descriptor and leave the credential itself on screen and in the retained state; the descriptor now stays readable and the value, including the one behind a copula or a separator, is replaced by the existing masking placeholder. Sentences that only mention a secret word are still shown unchanged.
- Remove the PATH block from the profile named by `FORGEL_CODE_PROFILE` — `--uninstall` again cleans the marked block out of the profile the override variable names, in addition to the six standard profile files, so a block left by a completed install or by an install that failed its fresh-shell check no longer survives.
- Point the README install, update and uninstall commands at the current `v0.1.1` release installer — the documented commands no longer fetch the stale install script, all three name one and the same install-script URL, and the guard in `tests/test_readme_install.py` fails the suite when any of them carries an older tag or a divergent install-script URL.

## [0.1.1] - 2026-11-23

### Fixed

- Fix install.sh so a new terminal finds forgel-code on PATH — The installer currently completes while the launcher directory never reaches PATH in a freshly opened terminal. It picks the profile file from $SHELL alone: on macOS a bash login shell never reads ~/.bashrc, and under `curl … | sh` $SHELL can be empty, sending the block to ~/.profile while the terminal reads ~/.zshrc. It also never checks that its own change took effect. This change makes the installer detect the real login shell, write the block into a profile file a new terminal actually reads, start a clean login shell afterwards and verify that `forgel-code` resolves, and fail with a message naming the edited file and the observed PATH when it does not. --uninstall removes the block from every profile file the installer can have written.
- Release audit: --uninstall no longer honors FORGEL_CODE_PROFILE. The old code removed the block — Add ${FORGEL_CODE_PROFILE:-} to the uninstall candidate set when it is set (deduplicate against PROFILE_NAMES), and add a test that installs and uninstalls with a custom profile path.
- Release audit: --uninstall omits ~/.bashrc, although the previous installer wrote the marked bl — Include ~/.bashrc in the legacy cleanup set for uninstall, update the README list, and extend CANDIDATE_PROFILES/test_uninstall_clears_every_candidate_profile to cover it.
- Make install.sh put forgel-code on PATH for a new terminal — The installer reports success while a new terminal cannot find forgel-code: the PATH block lands in a profile file the user's shell does not read on login and nothing verifies it. The change detects the real login shell, writes a duplicate-safe block into the files that shell reads, verifies the result in a fresh login shell with a loud failure message, and removes the block from every profile file on --uninstall.
- Make the install.sh PATH check strictly bounded and keep the profile byte-identical on re-install — The install.sh fix task was accepted, but the full change-set check of the 0.1.1 release rejected the result: the fresh-shell check is not strictly bounded (the watchdog writes predictable files in a shared temporary directory, ignores its own timeout status when deciding success, and can wait forever on a shell that ignores the soft kill signal), and a re-install over an existing profile leaves an extra blank line instead of keeping the rest of the file byte-identical. The fix must live in install.sh itself, with tests for each case, so the release can pass its full check and be published.
- Release audit: `remove_profile_block` and `uninstall_profile` remove a block whenever `# >>> fo — Only remove a block when both the start and matching end marker are present. If the end marker is missing, leave the file unchanged (or restore the original content), and add regression tests for an unmatched start marker on both install and uninstall paths.
- Release audit: The final task's recorded test run shows only `timed out after 120s` and partial — Run the complete suite with an adequate timeout, fix or shorten any slow/hanging bounded-check tests (for example by setting a short `FORGEL_CODE_TIMEOUT` in those tests), and record the completed passing output.
- Release audit: `bounded_run` does not make the watchdog's timeout decision authoritative. After — Have the watchdog record the final child/timeout status and wait for that status before deciding success, or measure the deadline in the parent and fail on any overrun; add a test whose checked shell returns just after FORGEL_CODE_TIMEOUT.
- Release audit: On a successful check, `bounded_run` clears `CHECK_CHILD` before `cleanup_check` — Run the checked shell in its own process group/session (with stdin/stdout detached so an interactive shell does not stop) and terminate that group after every outcome, including success; otherwise reliably enumerate and kill descendants before clearing `CHECK_CHILD`. Add a test with a profile that starts a background process.
- Release audit: README.md still documents `.../v0.1.0/install.sh` for the install command and fo — Update both documented commands to the current release installer (v0.1.1 or a versionless latest URL) and add a README guard test that asserts the install and uninstall commands use the release installer.
- Release audit: bounded_run clears CHECK_CHILD before calling cleanup_check, and install.sh deli — Start the checked shell in a dedicated process group/session, record that group for cleanup, call cleanup_check before clearing CHECK_CHILD or any state it reads, signal the group plus a descendant sweep on every exit path, and commit tests that start a background process from the checked shell and assert it is gone on both success and timeout.
- Release audit: install.sh's bounded_run still decides the timeout by testing for the timed-out — Make the watchdog write the final decision (timeout marker plus status), have the parent wait for that decision within a small bound derived from VERIFY_GRACE, and force CHECK_STATUS=124 whenever the bound elapsed regardless of the order of the child exit and the marker write. Add and commit the test whose checked shell exits just after FORGEL_CODE_TIMEOUT and assert install.sh fails with a message naming the limit.
- Release audit: The suite runtime regressed past the bound the release established. Task 2026112 — Bring the suite back under the documented bound (or raise the bound consistently in README/acceptance and confirm the audit's timeout), then record a passing run of the full suite within that bound. Do not state 'under 120 seconds' while the final suite takes 163 s.
